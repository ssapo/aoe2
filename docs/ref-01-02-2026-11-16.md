# REF-01 / REF-02 조사 (2026-11-16)

## REF-01 — `Arabia`와 `Arabian Desert`

**결론: 다른 맵이다. 합치지 않는다.** 두 이름은 리플 헤더의 맵 ID가 다르다. 정규화는 넣지 않았다.

근거:

- 저장 보고서(`site/data/report.json` + `profiles/*/report.json`, 분석된 166판)에서 경기 API 이름과 `analysis.map`을 비교하는 것은 소용이 없다. `scripts/collect.py`가 분석된 행의 `map`을 `analysis['map']`으로 덮어쓰기 때문에 166판 모두 두 값이 같다(Arabian Desert 113, Arabia 19, …).
- 그래서 API를 직접 다시 받고(`getRecentMatchHistory`, 프로필 10개, 중복 없는 1v1 RM 포함 수백 판) 리플을 몇 판 받아 `mgz` 파서로 `map.id`·`map.name`(= 헤더 `de.rms_map_id`)을 비교했다. 리플은 세션 스크래치패드에서만 열었고 저장소에 저장하지 않았다.

| 경기 | API `mapname` | 리플 `rms_map_id` / 파서 이름 | 시작(UTC) |
| --- | --- | --- | --- |
| 520592057 | `Arabia.rms` | 9 / Arabia | 11-12 |
| 521125276 | `Arabia.rms` | 216 / Arabian Desert | 11-14 |
| 521402349 | `Arabia.rms` | 216 / Arabian Desert | 11-15 |
| 521420102 | `Arabia.rms` | 216 / Arabian Desert | 11-15 |
| 521429166 | `Arabian Desert.rms` | 216 / Arabian Desert | 11-15 |

(`Arabian Desert.rms`로 내려온 판을 더 받으려 했으나 리플 서버가 429를 줘 위 한 판만 확인했다. 이름으로 보면 같은 값이다.)

- 파서 쪽은 안정적이다: ID 9는 Arabia, 216은 Arabian Desert이고 둘은 서로 다른 맵 스크립트다. 저장된 분석 경기에서도 두 이름이 같은 기간(10-23~11-16)에 함께 나온다.
- 어긋나는 쪽은 **API 파일 이름**이다. `Arabia.rms`가 실제로는 216(Arabian Desert)인 경우가 있다(표본 4판 중 3판). 즉 "API가 `Arabia`라 부르는 판 = 파서의 Arabia"는 성립하지 않는다.
- 영향: 비교·벤치마크는 분석된 행(`analysis.map` 사용)만 쓰므로 이미 파서 이름 기준이다. API 이름이 그대로 남는 곳은 분석되지 않은(목록만 있는) 경기 행의 `map`뿐이다. 이 행은 상위권 비교 표본이 아니므로 고칠 것이 없지만, 그 행의 `Arabia`를 "같은 맵"의 근거로 쓰면 안 된다.
- 남은 후보(하지 않음): 분석 안 된 행도 리플 헤더만 읽어(`civ_choice`처럼) 맵 이름을 채우는 일. 지금 쓰는 곳이 없어 하지 않았다.

## REF-02 — 상위권 기준 비교의 레이팅

이전: `scripts/ranked_benchmarks.py`가 `players.json`(랭킹 파일 수집 시점의 **현재** 레이팅)에서 2000 이상인 선수만 표본에 넣고, 표본의 `rating`도 그 값이었다. 프런트(`site/ranked-benchmarks.js`)는 `rating >= min_rating`만 보므로 레이팅은 **포함 여부**에만 쓰인다.

원인과 한계:

- 경기 행에는 기록 주인(`rating_before`/`rating_after`)의 경기 전·후 레이팅만 있고, **상대**의 경기 당시 레이팅은 저장하지 않았다(API `matchhistorymember[].oldrating`에는 있다).

고친 것(`method_revision` 4, 분석 개정은 그대로 30):

- `scripts/collect.py`의 `metadata`가 `players[].rating_before`(API `oldrating`, 값이 있을 때만)를 저장한다. 앞으로 갱신되는 행부터 채워진다.
- `ranked_benchmarks.py`의 `rating_for`: 경기 행에 경기 전 레이팅이 있으면 그것(`rating_basis: "match"`), 없으면 랭킹 파일의 현재 레이팅(`"current"`)으로 대신하고 표본마다 `rating_basis`를 남긴다. 2000 이상 여부를 이 값으로 정한다. 같은 숫자 안에서 두 출처를 섞지 않는다.
- 보존된 옛 표본: `match` 값은 그대로 두고, `current` 값만 랭킹 파일을 따라간다(이전 동작과 같다).
- 프런트·JSON 스키마 호환: `rating`은 그대로 숫자이고 `rating_basis`는 추가 필드라 프런트 수정이 필요 없다.

저장된 데이터에 적용한 숫자(메모리에서 다시 빌드해 비교, 파일은 건드리지 않음): 표본 233 → 233(빠진 것·새로 들어온 것 0). 기록 주인 쪽 117개는 `match` 기준으로 바뀌고 모두 2000 이상(최저 경기 전 레이팅 2,6xx대)이라 포함 여부는 그대로다. 상대 쪽 116개는 저장된 행에 경기 전 레이팅이 없어 아직 `current`다. 새 수집이 쌓이면 상대 쪽도 `match`로 바뀌고, 그때 "지금은 2000 이상이지만 경기 때는 아니었던" 표본이 빠지고 그 반대가 들어온다(과거 행은 API 목록에서 사라지면 되돌릴 수 없다).

남은 제약: 게임 빌드별 분류 없음, 30일 범위 제한(바꾸지 않음).
