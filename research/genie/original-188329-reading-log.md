## 1. AI 전체 갱신 0xd42a00 — 직접 읽음

근거: re-kit/re/out/d10.c:1~779 (다음 함수 0xd31d50 전까지).

확인한 순서:
1. 시간 누적·검색 관련 전역 초기화, 죽은 개체 조기 종료.
2. 재시도 목록 정리, 목표 관련 검사와 공격자 목록 정리.
3. 현재 위치 및 명령/그룹에 따른 상태 위치 저장.
4. 타이머 갱신: ai+0x178 증가, ai+0x168 증가, ai+0x174는 dt만큼 포화 감소.
5. 알림 목록(ai+0x28 개수, +0x30 배열, 원소 0x18바이트)을 가상 슬롯 +0x238로 처리.
   - 결과 2이면 계속, 3 또는 0xd이면 이번 순회를 끊는다.
   - 결과 4이면 처리 중 표시를 해제하고 버퍼를 합친 뒤 알림 정리 후 종료한다.
   - 반복 중 버퍼 합치기 0xd30790, 정리 0xd38990의 순서를 보존해야 한다.
6. 알림 정리 후 유닛의 실제 동작 목록을 다시 질의(+0x468, 추가 +0x8d8 조건). 필요하면 current_action(+0x44)을 비우고 current_order(+0x3c)를 정리한다.
7. 가상 슬롯 +0x248 호출. 이후 유휴 처리(+0x240), look-around, 현재 동작의 목표 검사, 시작된 건설 예약 제거.

**새로 확인한 차이:** 이 함수 본문에는 예약 명령 실행 함수 0xd384f0의 직접 호출이나 명령 실행 슬롯 +0x230 직접 호출이 없다. 엔진 unit_ai/update.rs는 알림 정리 뒤 run_orders를 호출하므로 구조가 다르다.
- 보충 확인: 0xd42a00~0xd443ee의 명령 1,442개를 읽어 0xd384f0 직접 호출 0개 확인. +0x238 호출은 0xd43528, +0x248 호출은 0xd43995.
- 한계: 하위 함수/가상 호출의 간접 효과까지 없다고 단정한 것은 아니다. +0x248 실제 대상 및 알림 처리의 호출 사슬을 추가로 읽어야 한다.
- 따라서 앞서 넣은 실험(매 틱 선행 검사)은 전체 갱신 내부 run_orders를 그대로 남겼으므로 원본 순서를 완전히 옮긴 구현이 아니다. 성능 개선이나 정찰병 문제 해결은 주장하지 않는다.

## 2. 매 틱 예약 명령 검사와 호출부 — 어셈블리 보충 확인

이 세 함수의 디컴파일 C는 현재 풀린 out*에서 발견하지 못했다. 아래는 디컴파일을 읽었다는 뜻이 아니라 원본 명령을 직접 확인한 기록이다.
근거: re-kit/ai-order-188329-disassembly.txt.

- 실제 상위 갱신 함수 0x114c0f0: 0x114c53d에서 동작 객체 갱신 0x11398c0을 호출.
- 0x114cf1c: AI 검사 0xd443f0 호출. 그 뒤 0x114cf2f에서 선수 차례를 검사하고, 자기 차례면 0x114cf5e에서 AI 슬롯 +0x20 호출.
- 검사 대상 조건: 유닛 종류 byte +0xf < 70 또는 내부 탑승 객체 +0x148 == 0. 단순히 모든 탑승 유닛을 제외하는 조건과 같지 않다.
- 0xd443f0: current_action(+0x44), 실제 동작 존재, 중단 가능 슬롯 +0x2e8, 0xd28660(ai,0), 그룹 조회와 그룹 검사 0x10dd870을 거쳐 0xd384f0 호출. 알림 개수 검사 없음.
- 0xd384f0: 명령 수락(결과 1) 후 0xd386d2에서 0xd38990(ai,0) 호출. 수락 후 알림 정리도 동작 규칙의 일부다.
- 0xd38990: 완료 알림과 current_order/current_action을 검사해 필요한 정지를 한 뒤 +0x164를 인자로 설정하고 알림 개수를 0으로 만든다.

정정: 인수인계의 0x12488e0은 이 AI 호출 순서를 읽을 올바른 상위 함수가 아니었다. 해당 C(h3.c:814~1308)는 개체 생명 상태 등 기본 갱신을 담고 있다.
미완료: 위 함수들의 새 디컴파일, 그룹 검사 의미의 독립 확인, 알림을 즉시 전달하는 경로와 엔진 with_side의 지연 전달 차이.

## 3. Hunt 갱신 0xbb6230 — state 1/4/8 직접 읽음

근거: re-kit/re/out_c/h1.c:1~803.

### D1: 걷는 중 목표를 잃었을 때 예약 명령
- state 4에서 하위 동작 반환값 4/5를 받으면 유닛 AI 존재와 예약 개수(0xd31a10)를 먼저 검사한다.
- 예약이 있으면 목표를 비우고 state 1로 바꾼다. 없으면 0xbb2c90 검색을 먼저 시도하고 실패 시 목표를 비워 state 11로 간다.
- 기존 D1 설명의 이 분기는 C에서도 확인된다.
- **주의:** state 1을 곧바로 단순한 사냥 종료라고 번역하면 부족하다. C 첫 분기에서 사람 선수이면 state 2로 바꾼다. C는 반환형 void로 복원되어 있어 외부 리스트가 받는 반환값까지 이 출력만으로 단정할 수 없다. 기존 메모에도 이 반환값 미확정이 남아 있다.

### D8: 반납 후 양 선택
- 반납 후 기존 목표가 남아 있으면 반납 목표를 비우고 state 4로 복귀.
- 목표가 없고 사람 선수이면 사라진 목표의 예약을 정리. 예약이 남으면 관련 AI 상태를 비우고 state 1로 간다.
- 일반 가축(class 0x3a), 목장 id 없음, AI 분류 분기가 -1인 경우 세 번의 검색이 존재한다.
  1. state=5, 기준 객체=반납 장소, 최선 거리의 정수 출력 포인터 있음.
  2. 첫 결과 없음 또는 거리 >= R이면서 2*정수 거리 >= R이면 같은 state=5를 기준 객체 없이 재검색.
  3. 결과 없음 또는 결과까지 거리 >= R이면 반납 장소를 기준으로 상태 제한을 푼 검색.
- R은 유닛 슬롯 +0x228, +0x2e0 결과의 큰 값. 경계는 엄격한 <로 결과를 유지하며 같으면 재검색 쪽이다.
- 세 번째 호출은 C에서 인자가 생략돼 있다. state=-1은 기존 어셈블리 조사와 대조된 값이며 C 호출 표기만으로 확인했다고 쓰지 않는다.
- 이 규칙이 해당 리플의 최초 자원 차이를 일으켰는지는 미검증.

## 4. 대상 검색 0xd22c20 — 함수 본문 직접 읽음

근거: re-kit/re/out_c/h2.c:536~1054.

- class, 관계, 상태, master id, 작업자 수 제한, 도달 가능성 등을 거른다.
- param_10(기준 객체)이 있으면 후보 평가 거리로 0x124d8d0(기준 객체, 후보)를 사용한다. 없으면 검색 캐시에 저장된 거리를 사용한다.
- 기준 객체까지 거리가 0이면 추가 거리값을 계산해 동률 비교에 사용한다. 그 보조값의 정확한 의미는 호출 인자가 C에서 사라져 아직 미확정.
- 보통 더 작은 거리를 선택. 동률 처리에는 후보 id 비교도 있으나, 0거리·보조값 분기가 섞여 있으므로 항상 단순한 (거리,id) 정렬이라고 일반화하지 않는다.
- param_7이 있으면 마지막에 최선 거리 float를 int로 변환해 저장한다. D8의 2*d는 실수 원거리 두 배가 아니라 이 정수 출력의 두 배다.
- C의 fStack_198=-NAN 및 float로 된 후보 id는 타입 복원 문제다. 숫자 NaN 연산으로 이식하면 안 된다.

보조 함수 0x124d8d0(h2.c:298~366)도 읽음:
- 중심 좌표 차이의 절댓값에서 두 개체 반크기의 합을 축마다 빼고, 각 축을 0 이상으로 자른 뒤 거리 계산.
- 중심 간 거리가 아니라 개체 외곽 간 거리다. D8 임계값 비교에 제곱 거리 함수를 대신 쓰면 안 된다.
- null 목표는 상수 반환. 그 상수의 수치와 제곱근 구현의 비트 일치는 추가 확인 대상.

## 5. MoveTo 갱신 0xb93260 — 상태 분기 직접 읽음

근거: re-kit/re/out_c/h3.c:397~702. 생성자 0xb92150 및 set_state 0xb931b0도 필요한 부분 읽음.

- state 1: 일반 동작(+0x60==0)이면 이동 완료 알림 0x1fa, action 0x262.
- state 2: state 3으로 전환.
- state 3: 경로 시작 결과 1이면 state 4, 아니면 state 13.
- state 4: 목표 이동 처리 뒤 걷기 슬롯 +0x658 결과 1이면 state 13, 결과 2이면 state 1 및 0x120d940 호출.
- state 13: 일반 동작이면 실패 알림 0x1f9.
- 이 갱신 본문에 별도의 대기 타이머 감소/대기 상태 재시도는 보이지 않는다. 단, 하위 걷기/경로 함수 내부의 대기까지 없다는 뜻은 아니다.
- set_state(4)는 동작 갱신 슬롯 +0x30을 즉시 호출한다. 한 틱씩 단순히 상태만 변경하는 모델로 옮기면 시점이 달라질 수 있다.
- 기존 D9(옛 MoveTo 대기 상태와의 차이)는 위 범위에서 뒷받침된다. 현재 엔진에 추가 구현하지 않음.
